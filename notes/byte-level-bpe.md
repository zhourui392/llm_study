# Byte-level BPE（字节级字节对编码）原理与工程参考手册

本文系统梳理现代大语言模型（GPT-2 / GPT-3 / GPT-4 / Llama 3 / Qwen / DeepSeek）最核心的分词算法——**Byte-level BPE（字节级字节对编码，BBPE）**。它属于纯统计规则算法，不含神经网络和可训练权重，负责连接“人类自然语言”与“模型整数世界”，充当**确定性的双向翻译器**（`文字 ↔ Token ID`）。

---

## 一、BPE 在 LLM 全链路中的位置与 Token 最小计算单位

### 1.1 端到端对称编解码链路

无论是用户输入还是模型生成，文本与 Token ID 之间都经过完全对称的逆过程——**UTF-8 编码 ↔ BPE ↔ UTF-8 解码**：

```text
【输入侧：Encode（文字 → Token ID）】
  原始文字 (str)                 "你好 world"
     │  1. 预分词（正则按词/标点/数字切粗块） + UTF-8 编码
     ▼
  字节流 (bytes: 0~255)          [E4 BD A0 E5 A5 BD] [20 77 6F 72 6C 64]
     │  2. 按 Merge Rank 两两合并，查表转为 Token ID
     ▼
  Token ID 序列 (list[int])      [108386, 1917]
     │
     ▼
═══════════════════  LLM 主体（Transformer 计算）  ═══════════════════
   Token ID → Embedding 查表 → L 层 Attention + FFN → LM Head → 采样
══════════════════════════════════════════════════════════════════════
     │
【输出侧：Decode（Token ID → 文字）】
  预测出的 Token ID 序列         [256, 152]
     │  1. 查词表把每个 Token ID 还原为字节片段并拼接
     ▼
  连续字节流 (bytes: 0~255)      [E9 BE] + [98] = [E9 BE 98]
     │  2. 统一按 UTF-8 解码（errors="replace"）
     ▼
  输出文字 (str)                 "龘"
```

### 1.2 为什么说 Token 是 LLM 计算的最小单位？

在目前主流自回归 LLM 中，**Token 就是模型在序列维度上“看得见、算得了、吐得出”的最小单位**：

1. **输入层**：每个 Token ID 去查 Embedding 表，变成 **1 个固定维度的向量**（例如 4096 维）。从查完表这一刻起，原始汉字、字母、字节边界全部消失，模型看到的只是形状为 `[batch, T, hidden_dim]` 的向量序列。
2. **主干计算**：
   - **Self-Attention**：计算量为 $O(T^2)$，直接由 Token 数量 `T` 决定；
   - **KV Cache**：显存里为**每个 Token** 缓存一份 `K` 和 `V` 向量；
   - **上下文窗口（如 128K）**：指的是最多容纳 128K 个 **Token**，而不是 128K 个字符。
3. **输出层**：每次前向推理只预测 **1 个 next token**。要生成 100 个 Token，模型就需要跑 100 次自回归前向推理。

> **解释三个常见现象**：
> - **API 按 Token 计费**：GPU 的实际算力与显存消耗由输入输出 Token 总数直接决定。
> - **数不清 `"strawberry"` 里有几个 `'r'`**：如果 Tokenizer 把 `"strawberry"` 切成了 `["str", "aw", "berry"]`，模型压根没逐字母扫描过，只能靠统计记忆去猜。
> - **生僻字更费算力**：1 个生僻字如果退化成 3 个 Token，就会占掉 3 个上下文位置、3 份 KV Cache，并多耗费 2 轮生成前向计算。

## 二、为什么是 Byte-level BPE？（对比与核心动机）

### 2.1 三代分词方案对比

| 方案 | 基础词表构成 | 总词表规模 | 序列长度 | 核心缺陷 / 优势 |
|---|---|---|---|---|
| **词级（Word-level）** | 完整单词 | 极大（数十万+） | 最短 | 遇未登录词只能变 `<UNK>` 丢信息；Embedding 矩阵爆炸 |
| **字符级 BPE（Char-level）** | Unicode 单字符 | 需预留数万槽位给基础字符 | 较短 | Unicode 超 14 万字符，基础字符挤占词表；未收录生僻字仍变 `<UNK>` |
| **字节级 BPE（Byte-level）** | **256 个 UTF-8 单字节** | **可控（32K～152K）** | **高压缩比** | **永远没有 `<UNK>`**；基础词表仅占 256 槽位，余下配额全留给高频词/子词 |

### 2.2 为什么区区 256 个字节就能改变游戏规则？

计算机中**任何文本按 UTF-8 编码后，本质上都是一串 `0 ~ 255` 的整数（字节）**（1 字节 = 8 bit，$2^8 = 256$ 种可能，不可能出现第 257 种值）：

- 英文 `'A'` → `[65]`（1 字节：`0x41`）
- 中文 `'你'` → `[228, 189, 160]`（3 字节：`E4 BD A0`）
- 生僻字 `'龘'` → `[233, 190, 152]`（3 字节：`E9 BE 98`）
- Emoji `'🚀'` → `[240, 159, 154, 128]`（4 字节：`F0 9F 9A 80`）

基于这个前提，Byte-level BPE 同时达成了两个关键目标：

1. **彻底消灭 `<UNK>`，实现 100% 无损编解码**：
   - 字符级词表如果没收录 `'🚀'`，字符又无法再往下拆，只能扔掉信息替换为 `<UNK>`。
   - 字节级词表把 **`0 ~ 255` 全部作为保底 Token**。就算训练语料里一次没见过 `'🚀'`，它也会变成 `[240, 159, 154, 128]` 这 4 个必然存在于基础词表中的编号，解码时拼回 UTF-8 原样还原成 `'🚀'`。
   - **类比**：只要基础词表有 `0 ~ 9` 这 10 个数字，任何十亿位整数都能拼出来，永远不需要 `<未知数字>`。

2. **基础词表极小（256 槽位），把 99.5% 的预算留给高频子词与整词**：
   - 模型的总词表预算受限于 Embedding / LM Head 显存（例如总预算 `50,000`）。
   - 字符级 BPE 光是覆盖常见多语言单字、标点、符号就要吃掉 `20,000 ~ 30,000` 个名额，还要背负大量低频生僻字；
   - **字节级 BPE 的保底单位固定只占 256 个名额**（在 50K 词表中仅占 **0.5%**），剩下的 **49,744 个名额（99.5%）** 全部按语料频率自由分配给 `" the"`、`"function"`、`"中国"` 等高频片段。
   - **类比**：字符级像给每种物体单独开模具（占满货架还总漏掉新品）；字节级只留 256 块通用乐高积木，把剩下几万个货架全摆上最畅销的成品套装。

## 三、核心算法拆解：预分词、训练、编码、解码

### 3.1 预分词（Pre-tokenization）

在统计和合并字节前，先用正则表达式把原始文本切分成互不跨越的粗粒度片段（chunk），**禁止 BPE 跨片段合并**：

- **防止标点粘连**：避免把 `dog.`、`dog!`、`dog?` 学成三个互相割裂的冗余 Token。
- **规范数字切分**：早期 GPT-2 允许任意长数字 `\p{N}+` 合并，导致 `1234` 与 `123` 切法混乱；GPT-4（`cl100k_base`）强制使用 `\p{N}{1,3}` 将数字按 1～3 位切块，大幅改善多位数算术泛化能力。
- **降低训练复杂度**：预分词后可对相同文本块先去重计数，训练扫描规模从“全量语料字节数”降到“唯一词块数”。

### 3.2 训练（Train）：统计频次 + 迭代合并

1. **初始化**：词表 `vocab` 放入 `0 ~ 255` 共 256 个基础字节（外加特殊 Token）。
2. **循环合并**（直到达到目标 `vocab_size`）：
   - 统计所有词块内部**相邻 Token 对 `(A, B)`** 的加权总频次；
   - 选出频次最高的一对 `(A, B)`，分配新编号 `new_id = 256 + step`；
   - 记录合并规则 `merges[(A, B)] = new_id` 和词表映射 `vocab[new_id] = vocab[A] + vocab[B]`；
   - 将所有词块中相邻且不重叠的 `(A, B)` 替换为 `new_id`。

训练完成后产出的核心资产只有两样东西：**词表（`vocab: ID ↔ bytes`）** 和 **有序合并规则（`merges: pair → new_id / rank`）**。

> **实现差异小注**：GPT-2 为让保存的词表文本可读、避开换行/控制符等不可打印字符，曾把 256 个字节一一映射到可见 Unicode 字符（因此空格在 GPT-2 词表里显示为 `Ġ`、换行显示为 `Ċ`）；现代实现（如 OpenAI `tiktoken`）直接对原始 `bytes` 运算，更简洁直观。

### 3.3 编码（Encode）：按 Merge Rank 优先级合并

编码一个新文本块时，**严格复现训练时的合并优先级**（而非直接找词表里的最长匹配）：
1. 把片段 `.encode("utf-8")` 转成初始字节 ID 列表；
2. 扫描当前所有相邻 pair，找出其中在 `merges` 中 **`new_id`（即 rank）最小**——也就是训练时最早学到的那一对；
3. 将这一对全局合并为新 ID；
4. 重复步骤 2～3，直到没有任何相邻 pair 出现在 `merges` 中为止。

### 3.4 解码（Decode）：先拼字节流，再统一 UTF-8 解码

用最简化的对称代码总结整个编码与解码核心：

```python
# Encode（文字 → Token ID）
byte_seq = text.encode("utf-8")                   # ① 先 UTF-8 编码成字节
token_ids = bpe_merge(byte_seq)                   # ② 再按 merge rank 合并成 Token ID

# Decode（Token ID → 文字）
byte_seq = b"".join(vocab[i] for i in token_ids)  # ① 先查表拼回连续字节流
text = byte_seq.decode("utf-8", errors="replace") # ② 再统一 UTF-8 解码成文字
```

**关键认知**：Decode 会先把所有 Token 的字节片段首尾拼接，再整体交由 UTF-8 字符集标准解码，而不是把单个 Token 独立翻译成字符。因此哪怕词表里从未收录 `'龘'`，只要模型依次输出对应字节碎片的 Token（如 `[E9 BE]` 和 `[98]`），拼接出 `E9 BE 98` 后依然能准确解出 `'龘'`。

## 四、核心疑问与直觉盲区精解

### 4.1 极少出现的生僻字拆成多个 Token，为什么模型依然能用？

单个字节（如 `233`、`190`、`152`）本身不带独立语义，但拆开后模型依然**完全有效**，原因有三层：

1. **信息零丢失，至少能“分得清、数得准、抄得对”**：
   - 如果是 `<UNK>`，`'龘'` 和 `'靐'` 在模型眼里完全相同，既不能计数也无法原样输出；
   - 在 Byte-level BPE 下，`'龘'` 是 `[233, 190, 152]`，`'靐'` 是 `[233, 157, 144]`，模型通过注意力机制能清晰区分、准确计数，并按顺序逐个吐出字节实现无损透传（生僻人名、古籍原文、特殊代码符号）。
2. **Transformer 本来就擅长“把多个子块融合成整体语义”**：
   - 英文高频词也常被拆成多个 Token（如 `"unbelievable"` → `["un", "believ", "able"]`，人名 `"Zhang"` → `["Z", "hang"]`）。
   - 在 Embedding 层它们只是独立碎片，但经过前几层 Self-Attention + 位置编码 + MLP 后，模型会自动将连续出现的 `(233, 190, 152)` 组合成 `'龘'` 的内部语义表征；生成时再自回归分步吐出这几个 Token。
   - 注意区分：**“没进词表” ≠ “训练时没见过”**。只要预训练语料里出现过该组合，模型就学得到它的含义与用法。
3. **代价是算力与长度（二八权衡）**：
   - 99% 高频字词合并成 **1 个 Token** → 极致省长度、省算力；
   - 1% 低频生僻字/新符号退化成 **2～4 个 Token** → 多花几步计算，换取全人类字符集的零 `<UNK>` 通用性。

### 4.2 退化时是变成“基础字节”还是“多个 Token 拼接”？

**两者是一回事，且实际中常见“逐级退化”的中间状态**：
- 256 个基础字节（ID `0 ~ 255`）**本身就是词表里的基础 Token**。
- BPE 编码时会尽量合并能合的字节对，因此一个 3 字节汉字 `[b1, b2, b3]` 存在 3 种形态：
  1. **1 个 Token**：`[b1 b2 b3]` 完整命中（如常见汉字，甚至整词合并）；
  2. **2 个 Token 拼接（半退化）**：UTF-8 编码具有强烈的局部前缀聚集规律。例如 `'龘'`（`E9 BE 98`）与 `'龍'`（`E9 BE 8D`）、`'龜'`（`E9 BE 9C`）共享前两字节 `E9 BE`；只要语料学到过 `E9 BE` 这个子块 Token，未见过 `'龘'` 也会优先合并为 **`[E9 BE]` + `[98]`**（2 个 Token）。同理，常见 Emoji 大多以 `F0 9F` 开头，生僻 Emoji 常切为 `[F0 9F]` + 后续字节；
  3. **3～4 个单字节 Token 拼接（完全退化）**：当相邻字节从未形成任何合并规则时，彻底回落到 `0 ~ 255` 的基础字节序列。

### 4.3 解码时的半截 UTF-8 字节与异常采样

1. **流式输出中途出现 ``（`U+FFFD`）**：
   - 当模型刚生成多字节字符的前半截 Token（如先吐出 `[E9 BE]`，尚未生成 `[98]`）时，单独解码会得到替换符 ``。
   - **工程解法**：流式推理层需维护增量 UTF-8 解码缓冲区（如 Python `codecs.getincrementaldecoder("utf-8")`），遇到不完整字节暂存不推送，等下一 Token 补齐字节后再推完整字符。
2. **高 Temperature / 欠训练模型的字节拼错**：
   - 若模型吐出 `[E9 BE]` 后采样到错误的合法尾字节（如 `97`），会拼出另一个偏僻字（`'龗'`）；若采样到违反 UTF-8 编码规则的非法字节组合，`errors="replace"` 会安全降级为 `` 而不会让程序崩溃。

## 五、工程实践要点与前沿演进

1. **词表规模权衡（Vocab Size Trade-off）**：
   - 词表越大，压缩率越高、上下文越耐用、生成步数越少；但入口 `Embedding`（$V \times d$）与出口 `LM Head` 参数和 Softmax 计算同步增大。
   - 演进趋势：从 GPT-2 的 `50,257`、Llama 2 的 `32,000`，扩展到现代多语言大模型普遍采用的 `100K ~ 152K+`（如 Llama 3 `128,256`、Qwen2.5 `151,643`）。
2. **跨语种“词元税”（Fertility）**：
   - 如果词表训练语料几乎全为英文，中文无法学到完整汉字合并，1 个汉字常退化为 2～3 个 Token，导致中文推理成本与上下文消耗成倍高于英文。充分混入多语种语料训练大词表是消除词元税的关键。
3. **Special Tokens（特殊标记）处理规范**：
   - 如 `<|endoftext|>`、`<|user|>`、`<|assistant|>` **绝对不走 BPE 字节合并**，必须在编解码前用正则切分直接映射；
   - 正则拼装时按长度**降序排列**（防止短前缀如 `<|end|>` 截断 `<|endoftext|>`）；
   - 训练完所有正常 merges 后连续分配特殊 Token ID，避免 `nn.Embedding` 矩阵出现无效空洞行。
4. **无 Tokenizer 前沿探索**：
   - 学术界也有直接以单字节输入/动态聚合字节块的探索（如 **ByT5**、Meta 的 **Byte Latent Transformer / BLT**），旨在彻底解决词元偏置与字符级计数难题，但目前工业界主力模型仍全部采用 Byte-level BPE。

### 6.1 极简教学版实测输出（`01-tokenizer/min_bpe.py`）

使用纯 Python 标准库编写的 `MinBPE`（45 行核心代码），在包含高频英文、中文及共享 UTF-8 前缀 `e9 be` 的 `"龍龜"`（**刻意排除 `'龘'` 与 `'🚀'`**）的小语料上训练 `vocab_size = 285`（256 基础字节 + 29 次合并），本地实测输出如下：

| 测试输入 | 原始 UTF-8 字节 | 实际编码 Token 序列 | 压缩比 | 行为验证 |
|---|---|---|---:|---|
| `'hello token'` | 11 字节 | `1` token：`[284]` | `11.00 B/tok` | 高频英文短语合并为 1 个 Token |
| `'你好大模型'` | 15 字节 | `1` token：`[278]` | `15.00 B/tok` | 中文经历单字(3B)→词(6B/9B)→整句(15B)逐级合并 |
